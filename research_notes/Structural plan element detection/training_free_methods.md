# Training-free, unsupervised and few-shot recognition of structural elements on vector construction drawings

Scope: techniques that exploit drawing structure (repetition, geometry, topology, grids, conventions, text) to find columns, footings (isolated/strip), walls, grade beams (longrines), rafts and slabs from PyMuPDF-extracted vector primitives, independent of colour and CAD layer names; plus synthetic-data and pseudo-labelling routes if learning becomes necessary.

Note on sourcing: 14 tool calls were used. Several primary PDFs (de las Heras 2013 CVC server; Dagstuhl GIScience 2018 wall paper; Springer IJDAR Lu 2007) could not be fetched, so claims about them rely on search snippets/abstracts. Items marked in "Inferences" are engineering judgement / general knowledge not verified by a fetched source in this session.

## 1. Repetition / clustering: grouping identical or congruent shapes, "find all instances like this"

### Takeaway
Classic symbol-spotting literature (Rusiñol & Lladós, CVC Barcelona) spots symbols directly on vector primitives by describing each primitive/closed region with a compact shape descriptor, hashing it, and voting for symbol locations — no training and no prior segmentation. For structural plans, where columns and footings are drawn as a few highly repeated closed shapes, this reduces to "canonicalise each closed polygon, hash its signature, cluster" — cheap and very effective; modern deep "panoptic symbol spotting" (FloorPlanCAD, GAT-CADNet, CADSpotting, VecFormer) needs labels and is the learning fallback.

### Cited Findings
- Rusiñol & Lladós, "Symbol Spotting in Technical Drawings Using Vectorial Signatures" (GREC 2005, LNCS): graphical symbols are represented by sets of vectorial primitives described by shape descriptors instead of pixels — [Springer](https://link.springer.com/chapter/10.1007/11767978_4)
- Rusiñol, Lladós et al., "A Region-Based Hashing Approach for Symbol Spotting in Technical Documents" (GREC 2007): a geometric hash function clusters similar shapes; compact per-primitive feature vectors are hash-table keys; querying a symbol uses a voting scheme to hypothesise where it lies; works without prior segmentation or a-priori knowledge — [Springer](https://link.springer.com/chapter/10.1007/978-3-540-88188-9_11); [Semantic Scholar](https://www.semanticscholar.org/paper/A-Region-Based-Hashing-Approach-for-Symbol-Spotting-Rusi%C3%B1ol-Llad%C3%B3s/847d8e365d4261b9d7fcb96a66ad089addd3a6cd)
- Rusiñol, Borràs, Lladós, "Relational indexing of vectorial primitives for symbol spotting in line-drawing images": combined numerical + relational description of 2D structures to retrieve symbol locations — [Semantic Scholar](https://www.semanticscholar.org/paper/Relational-indexing-of-vectorial-primitives-for-in-Rusi%C3%B1ol-Borr%C3%A0s/271b79387169b4b902744526e4a7b708af25fe60)
- Further training-free spotting variants from the same school: hashing serialized graphs (Pattern Recognition 2013) and graph-path hashing / Bag-of-GraphPaths descriptors — [ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S0031320312004359); [ResearchGate](https://www.researchgate.net/publication/224265575_Symbol_Spotting_in_Line_Drawings_Through_Graph_Paths_Hashing); [Springer](https://link.springer.com/chapter/10.1007/978-3-642-36824-0_20)
- Early CAD symbol-spotting relied on handcrafted shape/structure descriptors with sliding-window search or graph matching; CAD drawings are vector graphics of segments, arcs and circles — [CADSpotting, arXiv 2412.07377](https://arxiv.org/html/2412.07377v1)
- Learned alternatives (require labels): GAT-CADNet treats a CAD drawing as a graph of primitives, maps vertex features to semantic labels and cascades attention scores into instance prediction — [arXiv 2201.00625](https://arxiv.org/abs/2201.00625); VecFormer uses a line-based representation of primitives to preserve geometric continuity, arguing rasterisation/graph/point representations lose structure or are costly — [arXiv 2505.23395](https://arxiv.org/html/2505.23395); text-enhanced spotting adds text primitives as a modality — [arXiv 2510.11091](https://arxiv.org/pdf/2510.11091), [arXiv 2607.12678](https://arxiv.org/pdf/2607.12678)
- Turning-function distance (Arkin, Chew, Huttenlocher, Kedem, Mitchell): polygon represented by cumulative tangent angle vs. normalised arc length; invariant to translation and scale; rotation becomes a vertical shift, so the minimal L2 distance over start-point shift t and rotation θ gives a rotation-invariant similarity — [Stony Brook implementation page](https://www3.cs.stonybrook.edu/~algorith/implement/turn/implement.shtml); [Mitchell, Polygon Matching (U. Waterloo)](https://student.cs.uwaterloo.ca/~cs763/Projects/phil.pdf)
- Locality-sensitive hashing of polygon shape signatures enables efficient similar-polygon retrieval at scale — [arXiv 2101.04339](https://arxiv.org/pdf/2101.04339)

### Inferences
- **Practical recipe (numpy/shapely):** (1) polygonise closed paths (PyMuPDF `get_drawings()` gives `re`/`l`/`c`/`qu` items with `closePath`); also `shapely.ops.polygonize(unary_union(lines))` to recover closed faces from line soup. (2) Canonical signature per polygon: rotate into its minimum-rotated-rectangle / PCA frame, record (w, h) sorted, area, perimeter, vertex count, convexity (area / hull area), rectangularity (area / MRR area), circularity 4πA/P², Hu moments (log-scaled) or a resampled turning function / centroid-distance Fourier descriptor (|FFT| magnitudes are rotation & start-point invariant). (3) Quantise and hash (e.g. round w,h to 1 cm model units) → exact-congruence groups in O(n); or DBSCAN/HDBSCAN on the descriptor vector for near-congruence. (4) Group statistics: group size (count), size, spatial arrangement. Columns = many small congruent compact polygons (square/rect/circle 0.2–1.0 m); isolated footings = fewer, larger congruent squares/rectangles (1–4 m) that each *contain* a column-sized polygon; this nesting is a much stronger cue than shape alone.
- **"Find all like this" (few-shot, one example):** user clicks one instance; take its *composite* signature = the set of primitives within its bbox (+ margin), normalised to its frame; spot candidates by hashing a pivot primitive (e.g. the outer rectangle) and verifying the rest with a Hausdorff / Chamfer distance in the pivot's frame (`shapely.hausdorff_distance`). Complexity ~O(n·k) with an STRtree.
- Hu moments are unstable for near-symmetric shapes (squares vs circles similar in several invariants) and for polygons with few vertices; for construction glyphs (mostly rectangles/circles/L/T), simple sorted-(w,h)+vertex-count+rectangularity keys outperform generic invariants and are easier to debug.
- Failure modes: same glyph drawn with different segmentation (4 lines vs 1 closed path vs rectangle + hatch) → normalise by first merging collinear touching segments and polygonising; overlapping annotations (dimension lines crossing a column) break closure → polygonize after snapping endpoints (tolerance ~0.5–1 pt) and allow "almost-closed" loops; text boxes, title-block cells and table cells also produce repeated rectangles → filter by location (inside title block/table bbox) and by grid alignment.

### Gaps
- No quantitative precision/recall figures for Rusiñol-style vectorial hashing were retrieved in this session (the papers report them on GREC/SESYD datasets; not fetched).
- No sourced benchmark comparing Fourier vs turning-function vs Hu descriptors specifically on CAD construction glyphs was found.

## 2. Recovering objects from line soup: walls from parallel pairs, gap closing, polygonisation, rooms, hatching as material cue

### Takeaway
Wall detection from vector plans is overwhelmingly done by pairing parallel segments whose spacing falls in a thickness range and whose projections overlap, after gap-filling/merging collinear fragments; then walls are polygonised and rooms/slabs obtained as faces of the resulting planar arrangement. Hatching (thin, equispaced parallel strokes whose endpoints lie on a contour) is recognisable purely geometrically and is a strong material cue (e.g. hatched band between columns = shear wall/voile).

### Cited Findings
- In a vector floor plan every wall is represented by two parallel line segments; approaches: detect parallel pairs then apply text + graphical rules; Hough + vectorisation; keep only pairs with black pixels in between; pairs separated by a distance in a predefined range — [search summary citing Dagstuhl GIScience 2018 and related](https://drops.dagstuhl.de/storage/00lipics/lipics-vol114-giscience2018/LIPIcs.GISCIENCE.2018.33/LIPIcs.GISCIENCE.2018.33.pdf) (primary PDF could not be parsed)
- The mapping between pairs of segments and walls is not bijective — two consecutive walls may share one segment — [ResearchGate figure](https://www.researchgate.net/figure/The-mapping-between-pairs-of-segments-and-walls-is-not-bijective-eg-the-walls-ab-and_fig5_256688203)
- de las Heras, Fernández, Valveny, Lladós, Sánchez, "Unsupervised Wall Detector in Architectural Floor Plans" (ICDAR 2013): exploits that walls are a repetitive element, naturally distributed in the plan and modelled by straight parallel lines — [CVC PDF](https://refbase.cvc.uab.cat/files/HFV2013.pdf) (server unreachable; claim from search snippet); [ResearchGate](https://www.researchgate.net/publication/261346690_Unsupervised_Wall_Detector_in_Architectural_Floor_Plans)
- Concrete vector pipeline with thresholds (Tang, Wang, Cosker, Li, "Automatic structural scene digitalization", PLOS ONE 2017 — **retracted 28 May 2025 over peer-review integrity**, so treat as engineering recipe, not validated evidence): gradient filter keeps near-axis lines (π/12); drop lines <2 mm; gap-fill & merge (1 mm, 5 iterations); remove evenly-spaced multi-parallel groups (windows); drop <90 mm; keep connected segments; second gap fill (90 mm gaps, 50 mm merge) to bridge doors; wall pairs = parallel lines 100–400 mm apart with >400 mm overlap; build wall polygons; raster check at 4096² via connected components; 2.3 s per plan; deployed at 70–98k requests/week — [PLOS ONE](https://journals.plos.org/plosone/article?id=10.1371%2Fjournal.pone.0187513)
- Lu et al. (Tong Lu, Chiew-Lan Tai et al.) proposed a shape-based method to detect parallel pairs (PPs) of structural elements such as shear walls and bearing beams in construction structure drawings; another Lu et al. work splits a structural drawing into segments by detecting grid symbols and extracts columns, beams and slabs with OCR — [IJDAR 9:31–47 (2007)](https://link.springer.com/article/10.1007/s10032-006-0029-6); summary via [MDPI Appl. Sci. 10(6):2066](https://www.mdpi.com/2076-3417/10/6/2066) and [ResearchGate](https://www.researchgate.net/publication/220163522_Automatic_analysis_and_integration_of_architectural_drawings)
- Lu et al.'s system detects parallel line pairs as walls first, then recognises remaining elements by matching predefined symbols; Macé et al. and Or et al. used contour tracking + geometric constraints for rooms — [PLOS ONE related-work section](https://journals.plos.org/plosone/article?id=10.1371%2Fjournal.pone.0187513)
- Hatching recognition criteria: a group of thin, equispaced, parallel slanted bars (slant 30–60°) whose endpoints lie on the hatched area's contour; hatch patterns are standardised (ASME Y14.2) — [ResearchGate figure (Dori/Liu MDUS line)](https://www.researchgate.net/figure/llustration-of-detection-of-a-group-of-hatching-lines_fig6_220509852); [EngineeringTechnology.org](https://engineeringtechnology.org/engineering-graphics/section-views/standard-hatch-patterns/); knowledge-based crosshatch recognition — [Springer BFb0033267](https://link.springer.com/chapter/10.1007/BFb0033267)
- In a 2026 training-free structural-plan pipeline, hatched bands between adjacent columns are classified as shear walls with thickness from the 90th-percentile hatch offset; short diagonals (4–22 mm paper) are erased before chaining; walls are detected before beams so wall footprints aren't misread as wide members; minimum member length 450 mm; fragment chaining tolerates gaps up to 450 mm — [Talebi-Kalaleh & Mei, arXiv 2608.17237](https://arxiv.org/html/2608.17237)
- Wall detection from 2D CAD for 3D models is also done with learned detectors (ResNet-50 classification, YOLOv3) — [ISARC 2022](https://www.iaarc.org/publications/fulltext/021_ISARC%202022_Paper_6.pdf); semi-supervised transformer wall segmentation with limited data — [Xie et al., CACAIE 2025](https://onlinelibrary.wiley.com/doi/10.1111/mice.13397)

### Inferences
- **Parallel-pair algorithm (Python):** normalise segments (merge collinear overlapping/touching ones: bucket by angle (1°) and signed offset (ρ), then 1-D interval union); for each angle bucket, sort by ρ; candidate pairs = ρ-difference in [t_min, t_max] (e.g. 0.1–0.6 m for walls, 0.2–0.8 m for grade beams/strip footings) with projection overlap ≥ max(0.3 m, 50% of shorter); prefer the *nearest* partner (greedy by smallest gap) to handle the non-bijective sharing; emit the overlap rectangle as a wall/strip piece; then `unary_union` pieces and snap at junctions (T/L/X). Complexity O(n log n) per angle bucket with sorted sweep; worst case O(n²) in dense hatching — so remove hatch groups first.
- **Medial axis/skeleton alternative:** once a band polygon exists (e.g. from polygonize), its centreline can be approximated by `shapely` `buffer(-w/2)` tests or by Voronoi of densified boundary (`shapely.voronoi_polygons`) clipped to the polygon; width = 2× distance of skeleton to boundary; constant-width bands ⇒ wall/strip/beam, width jumps ⇒ junction or pad.
- **Gap closing:** snap endpoints within ε via KD-tree (scipy.spatial.cKDTree) + extend segments to intersect near-miss neighbours (≤ ε along direction); then `shapely.ops.polygonize_full` returns polygons plus dangles/cut-edges/invalid rings — dangles are diagnostic of unclosed outlines.
- **Rooms/slab panels:** faces of the planar arrangement of wall/beam centrelines (or of the union of all "thick" elements, take `building_outline.difference(union_of_elements)` → connected free regions) give slab panels; raft = one large polygon containing most columns, often hatched/stippled or bounded by thick outline, with area ≳ 50% of footprint.
- **Hatch detector:** cluster segments by angle; within an angle cluster, build 1-D sequence of offsets; runs with near-constant spacing (CV < 10%) and ≥ 4 members whose endpoints lie on a common boundary polygon = hatch region; region hull → hatched area. Concrete "stipple" (dots/small triangles) = many tiny closed paths / zero-length lines with high density inside a region → detect via density of micro-primitives per unit area. PyMuPDF often exposes PDF pattern fills (`fill` with pattern) as expanded paths or not at all — check both.
- Failure modes: double lines that are not walls (dimension/extension line pairs, stair stringers, table borders, title-block frames, text underlines) → require min length, exclude thin line weights typical of dimensions, exclude pairs with arrowheads/ticks; hidden (dashed) footing outlines under walls are drawn as dash chains → merge dash sequences into lines first; curved walls need arc pairing (concentric arcs with radius difference in range).

### Gaps
- Precision/recall of de las Heras 2013 and the Dagstuhl 2018 wall detector could not be retrieved (sources unreachable/unparseable).
- No source found that specifically detects concrete stipple on vector PDFs; recipe above is inference.

## 3. Grid-axis reasoning, topological/structural rules, constraint/logic/probabilistic interpretation, knowledge-based systems

### Takeaway
The strongest training-free anchor on structural plans is the grid: dash-dot axis lines with labelled bubbles define a lattice; columns sit at (or near) intersections; beams/walls connect supports; unsupported members are rejected. A 2026 fully training-free pipeline built exactly this way reports ≥92% column recall at 99.7% precision (on synthetic held-out plans). Knowledge-based engineering-drawing interpretation (Dori, Tombre, Kanungo/Haralick, Lu) is the classical lineage.

### Cited Findings
- Talebi-Kalaleh & Mei (U. Alberta), "Training-Free Agentic Computer Vision for Structural Component Detection in 2D Structural Framing Plans" (arXiv 2608.17237, 2026) — ordered pipeline: scale → grid → column glyphs → members → symbol grammar → topology — [arXiv HTML](https://arxiv.org/html/2608.17237):
  - Scale from dimension consensus: printed distance strings paired with thin measurement lines, validated by offset/angle/terminator geometry, MAD outlier filtering and snap-to-standard scales; two-point calibration fallback. Scale within 0.1% on every test drawing.
  - Grid: dash-dot stroke chains (dash array ≥4 entries) anchored by a bubble (circle radius 3–7.5 mm) with a 1–2 char label; **grid family assigned by label content (letters vs numbers), not direction**, so rotated wings work; bay distances from the intersection lattice.
  - Columns: closed glyphs with principal extents 60–2000 mm (long) / 30–2000 mm (short), aspect ≤ 6; interior width sampled at 5 stations along the principal axis — pinched middle = wide-flange, uniform = rectangle, single wide end = tee; hollow glyphs via concentric white knockouts.
  - Members: unfilled polygon footprints at true width or centreline chains of collinear strokes; stroke-weight classes via drawing-specific histogram percentiles unioned with fixed windows.
  - Topology: endpoints snap to supports (columns within half-extent + 600 mm, walls/beams within half-width + 600 mm) in precedence order; interior columns split continuous spans; members bearing on neither end are rejected; column-extent guard (bbox + 3 m) removes drawing furniture.
  - Symbol grammar of 11 explicit rules (e.g. X-marked rectangles ≥1 m sides = openings; angle-gated dedup; wall-coverage deletion of coincident beams).
  - Optional VLM refinement restricted to 12 typed operations, each admitted only by deterministic geometric guards (e.g. additions need ≥9 of 15 axis samples with ink within 2.4 mm) and a separate judge call; fails closed.
  - Results on the 50-plan held-out synthetic half: columns 92.2% R / 99.7% P; beams 88.6% R / 99.0% P; walls 100/100; braces 100/100; openings 100% R / 96.4% P. Limitation: test plans are generator-made, not independently drafted; new notations need explicit rule updates.
- Lu et al. segmented structural drawings by detecting grid symbols and used OCR to locate columns, beams and slabs; recognised structural objects then integrated same-floor and cross-floor drawings for 3D reconstruction — [IJDAR 2007](https://link.springer.com/article/10.1007/s10032-006-0029-6); [MDPI summary](https://www.mdpi.com/2076-3417/10/6/2066)
- BlueprintAgent (arXiv 2609.07362) uses the axis grid as the spatial skeleton: columns and beams represented by grid intersections, axis labels and node sequences rather than pixel coordinates, with constraint-triggered revisits — [arXiv 2609.07362](https://arxiv.org/pdf/2609.07362)
- Classical knowledge-based interpretation: Kanungo, Haralick & Dori, "Understanding Engineering Drawings: A Survey" (GREC 1995); Dori & Tombre, "From Engineering Drawings to 3-D CAD Models: Are We Ready Now?" (CAD 1995); Tombre, "Technical Drawing Recognition and Understanding: From Pixels to Semantics" — [ResearchGate survey](https://www.researchgate.net/publication/2755695_Understanding_Engineering_Drawings_A_Survey); [Semantic Scholar (Tombre)](https://www.semanticscholar.org/paper/Technical-Drawing-Recognition-and-Understanding:-to-Tombre/89b14e98b9a65d0adf05a9257e0675ee52c0580a); "Knowledge Organization and Interpretation Process in Engineering Drawing Interpretation" — [Academia](https://www.academia.edu/112535459/Knowledge_Organization_And_Interpretation_Process_In_Engineering_Drawing_Interpretation); "Analysis of engineering drawings: state of the art and challenges" — [Springer](https://link.springer.com/chapter/10.1007/3-540-64381-8_54)
- Semi-automatic structural component detection from CAD for as-is BIM exists as a separate line — [ResearchGate 317574996](https://www.researchgate.net/publication/317574996_A_Semi-Automatic_Approach_to_Detect_Structural_Components_from_CAD_Drawings_for_Constructing_As-Is_BIM_Objects)
- Structural conventions (French): isolated footings (semelles isolées) sit under columns (poteaux); strip footings (semelles filantes) under walls/voiles or rows of columns; longrines are RC beams bearing on isolated footings and carrying load-bearing walls; a raft (radier) is used when footing area exceeds ~50% of the building footprint — [Wikipédia: Semelle de fondation](https://fr.wikipedia.org/wiki/Semelle_de_fondation); [Hamil blog](https://blog.hamil.fr/2018/02/07/les-fondations/); [GuideBeton](https://www.guidebeton.com/fondations-superficielles)

### Inferences
- **Foundation-plan rule set (for a factor-graph / scoring CSP):**
  - Column C: small compact closed polygon, repeated, near grid intersection (distance < ~0.5 m), often filled/hatched, contained in a footing.
  - Isolated footing F: larger closed polygon (typ. 0.8–4 m side), contains exactly one column (or a pedestal+column pair = nested concentric rectangles), repeated with a few size classes (F1, F2… labels).
  - Strip footing S: long constant-width band (0.4–1.2 m), containing a narrower wall band (voile) on its medial axis or dashed wall outline; follows grid lines.
  - Grade beam / longrine L: constant-width band (0.2–0.6 m) whose two ends terminate on footings/columns and that does *not* rest on a wider band; typically connecting adjacent F's along grid lines.
  - Raft R: one large polygon covering most columns, area ≥ ~50% of footprint, may be thickened under columns (drop panels).
  - Slab: faces bounded by beams/walls; often carry a label with thickness ("ép. 20", "e=0.20").
- **Implementation:** build candidate sets geometrically, then a graph (networkx) of containment ("inside"), support ("ends on") and alignment ("on grid axis") relations; score each hypothesis with weighted rule satisfaction and resolve conflicts with a simple ILP or greedy max-weight (e.g. PuLP/OR-Tools) — "each band is exactly one of {wall, strip, grade beam, other}; a footing must contain ≥1 column". Answer-set programming (clingo, has Python API) fits naturally for defeasible rules ("a band is a strip footing unless it is supported at both ends by footings and narrower than X"); Markov logic / CRF over the relation graph is the probabilistic analogue if a few labelled sheets exist for weight tuning.
- Grid detection without dash metadata: PyMuPDF exposes `dashes` on each drawing path — dash-dot patterns ("[a b c b] 0") identify axis lines directly; fallback = long lines spanning > 60% of the drawing extent with circle+short text at an end.
- Failure modes: columns deliberately off-grid (edge columns, eccentric footings), multiple grids with skewed wings (handle via label-based families as in 2608.17237), plans without grids (small residential) → fall back to repetition+containment; foundation plans mixing upper-floor columns shown dashed.

### Gaps
- No published training-free system specifically for *foundation* plans (footings/strips/longrines/rafts) was found; the 2608.17237 system targets framing plans (columns/beams/walls/braces) and was evaluated only on generator-made drawings.
- No source found applying ASP/clingo or MLN specifically to construction drawings in this session (known in general graphics-recognition literature, but unverified here).

## 4. Style-independent cues: line weight, closed/open, fill vs outline, size distribution, text vocabulary, legends and schedules

### Takeaway
Line weight, dash pattern, closure, fill, and relative size are all exposed per primitive by vector PDFs and are robust across offices when used *relatively* (drawing-specific percentiles) rather than with absolute thresholds; text labels near shapes (poteau/P1, semelle/S1, voile/V, longrine/L, radier) and schedules give near-free semantic labels.

### Cited Findings
- Vector PDF input preserves machine-readable text, line weights and stroke attributes; member stroke-weight classification uses drawing-specific histogram percentiles unioned with fixed windows; section/material assignment from parsed designations, neighbouring labels, glyph shape or defaults; section assignment requires an exact local text match — [arXiv 2608.17237](https://arxiv.org/html/2608.17237)
- Drawing entities (solid, dashed, dot-dashed lines, dimensions, hatches, symbols, text) have semantic meaning defined by standards — [Vectorization of Scanned Engineering Drawings (ResearchGate)](https://www.researchgate.net/publication/275329971_Vectorization_of_Scanned_Paper-Based_Engineering_Drawings_-_Contemporary_Software_Abilities)
- Text-enhanced symbol spotting shows text primitives materially help symbol recognition in CAD drawings — [arXiv 2510.11091](https://arxiv.org/pdf/2510.11091); [arXiv 2607.12678](https://arxiv.org/pdf/2607.12678)
- French structural vocabulary (semelle isolée / filante, longrine, radier, poteau, voile) and their structural relationships — [Wikipédia](https://fr.wikipedia.org/wiki/Semelle_de_fondation); [Univ. Chlef foundations chapter](https://www.univ-chlef.dz/fgca/CHAPITRE-2-FONDATIONS.pdf); [Univ. Batna 2 chapter 4](https://staff.univ-batna2.dz/sites/default/files/dimia-mohammed-salah/files/chapitre_4_calcul_des_fondations_superficielles.pdf)
- Automated table/schedule detection and extraction from documents is an active patent area — [US 11977533](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/11977533)

### Inferences
- **Line-weight cue:** compute histogram of stroke widths (PyMuPDF `width`) per sheet; cut-plane elements (columns, walls in section) are typically drawn heaviest; outlines below (footings under slab) are medium or dashed; dimensions/hatch/text are thinnest. Use rank/percentile, not absolute mm.
- **Fill cue:** `fill` not None → solid poché (common for columns/walls in section). Must be colour-independent: treat any non-white, non-background fill as "filled", ignore hue.
- **Size-distribution cue:** plot log(area) of closed polygons — distinct peaks = element classes (columns ≪ footings ≪ rooms/panels); peaks + repetition counts give class candidates without thresholds tuned per drawing (e.g. Gaussian mixture on log-area × count).
- **Label vocabulary (seed lexicon; regex on `get_text("words")`):** FR — poteau/P, semelle (isolée/filante)/S/SI/SF, longrine/L/LG, voile/V, radier/R, dalle/D, poutre/PT/Pt, gros béton, béton de propreté, "ép."; EN — column/C, footing/F/PF (pad), strip footing/SF, grade beam/GB, tie beam/TB, wall/W, raft/mat, slab/S (note "S" collides between FR semelle and EN slab — detect sheet language first from frequent words); also DE (Stütze, Einzelfundament, Streifenfundament, Bodenplatte, Wand), ES (pilar, zapata aislada/corrida, viga de atado/riostra, losa, muro). Associate labels to nearest shape via leader lines (a thin line from text bbox to a shape) or containment/nearest centroid within a radius.
- **Legends/schedules:** find tables (grid of thin lines with text in cells, or `page.find_tables()` in PyMuPDF ≥1.23); a legend row pairing a small sample glyph with a word lets you "few-shot" spot every instance via Section 1 signature hashing — i.e. the legend is a zero-cost training set. Footing schedules (type, L×B×H, rebar) map mark → dimensions, which can then verify detected polygon sizes.
- Failure modes: PDF text may be vectorised to curves (no extractable text) → need OCR fallback or glyph clustering; labels placed on tags (circle/hexagon) far from elements; line weights flattened by some PDF exporters (all 0 or all same) → rely on geometry/topology.

### Gaps
- No source quantified cross-office variability of line-weight conventions.
- No curated multilingual structural-label lexicon was found; the list above is compiled from domain knowledge and FR sources, not a published resource.

## 5. Synthetic data generation and self-training / pseudo-labelling

### Takeaway
Procedurally generated drawings with exact ground truth are established practice for floor-plan recognition and were even the *evaluation* basis of the 2026 training-free structural system; if learning is needed, a deterministic pipeline (Sections 1–4) can pseudo-label real sheets, keeping only high-confidence, rule-consistent detections to train a vector model (e.g. GNN/transformer over primitives), iterating teacher→student.

### Cited Findings
- 2608.17237 evaluates on 100 synthetic plans generated from known rules, split into development (PD-50) and a seed-disjoint held-out half; rules frozen before held-out generation — shows a generator is useful for regression-testing rule pipelines — [arXiv 2608.17237](https://arxiv.org/html/2608.17237)
- Synthetic training data generation for floor-plan ML is patented (Autodesk-style: US 12518066) to address data scarcity; procedurally generated synthetic datasets are highly configurable (room shapes, sizes, configurations, noise patterns) and models trained purely on them achieve competitive performance on unseen real data — [US 12518066](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/12518066)
- Architext procedurally generates diverse floor plans with CAD-like programmatic scripts giving clean annotations and controlled geometric variation; synthetic pre-training mitigates domain shift for data-efficient adaptation — [arXiv 2607.06483](https://arxiv.org/pdf/2607.06483)
- Fully automated synthetic BIM dataset generation framework (Automation in Construction 2025) — [ScienceDirect S0926580525006247](https://www.sciencedirect.com/science/article/abs/pii/S0926580525006247)
- Large public datasets usable for pre-training or generator statistics: FloorPlanCAD (panoptic symbol spotting, vector CAD) — [ResearchGate](https://www.researchgate.net/publication/358999306_FloorPlanCAD_A_Large-Scale_CAD_Drawing_Dataset_for_Panoptic_Symbol_Spotting); ResPlan, 17,000 residential vector-graph floor plans — [arXiv 2508.14006](https://arxiv.org/html/2508.14006v1)

### Inferences
- **Procedural foundation-plan generator (Python):** sample orthogonal grid (n_x, n_y bays 3–8 m, optional skew wing) → columns at intersections (random sizes 0.2–0.6 m, drop some, add off-grid edge columns) → footings sized from random "loads" into 2–5 type classes with marks F1..Fk → strip footings under randomly chosen perimeter/axis wall lines → longrines between neighbouring isolated footings → optional raft variant → slabs as grid faces. Render to PDF with *domain randomisation*: line weights, dash patterns, fill vs hatch vs empty, hatch angle/spacing, stipple, colour (then ignore it), layer-free output, text language (FR/EN/DE), label placement (inside, leader, tag bubble), dimension chains, title block, legend & schedule tables, clutter (rebar callouts, section marks), random segmentation (rectangle as 1 path vs 4 lines vs broken dashes), small endpoint jitter/gaps. Use reportlab/cairo or write PDF via PyMuPDF `Shape` so extraction path equals production path. Ground truth = per-primitive class + instance id → trains GNN/transformer symbol-spotting models (GAT-CADNet/VecFormer-style) directly.
- **Pseudo-label loop:** run deterministic pipeline on real sheets → keep instances satisfying ≥k independent cues (repetition group + containment + grid alignment + label agreement) → train primitive classifier → predict on all sheets → re-admit only predictions passing the rule guards (the "guarded" admission idea from 2608.17237) → iterate. Use disagreement between model and rules as an active-learning queue for human review.
- Risk: generator bias (models learn generator idiosyncrasies; 2608.17237 itself notes generator-made test plans are a limitation) — always hold out real drafted sheets for evaluation.

### Gaps
- No paper found generating synthetic *foundation/structural* plans specifically for training (only floor plans and the 2608.17237 evaluation generator).
- No published quantitative result of pseudo-labelling from a rule-based CAD pipeline was found.
